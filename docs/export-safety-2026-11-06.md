# 更新与大数据导出修复：本地验收

本次继续保留工作区已有消息运行修复，验收基线为 8827d69。用户随后已授权提交和发布；本文描述本地验收结果，实际发布提交和状态以 Git 历史及 Pages 构建记录为准。

## 更新是否删除历史

历史存储仍使用 ShikiMessageNextV1/chat_data 与 SHIKI_NEXT_ 键，未重命名、迁移、清空或升级数据库结构。Service Worker 未增加清理存储操作。上传源代码不等于上传或删除浏览器里的个人消息。继续使用原网址、原浏览器的站点数据。

隔离 Chromium 测试先从 Git HEAD（8827d69）加载旧网页，创建 2048 条历史消息，其中 256 条附带合计约 32MB 合成媒体字符串；然后在同一来源和数据库下加载当前本地代码。消息 ID 序列与媒体数量一致。随后实际点击导出、超限失败与取消，存储中的 ID 序列仍一致。

这不是对用户真实手机数据的读取或绝对无丢失保证；没有在用户真实浏览器里进行恢复或迁移。

## 已确认的导出高内存路径

旧 exportConversation 对 chatMessages 使用 JSON.parse(JSON.stringify(value))，把消息内媒体载荷一起深拷贝。随后整包 JSON.stringify 检查上限，UI 再次进行带缩进 stringify 与 Blob 构造。虽然界面说消息媒体不包含，实际导出路径并未先去掉消息内媒体，重复复制可能造成很高的内存峰值。

## 修改

- 先按现有轻量消息格式投影消息，媒体替换为明确占位；保留 ID、文字、身份、引用等适用字段，不修改源消息。修复长文字导出/校验中原有 30000 字符静默截断。
- 当前会话使用只读内存快照，避免为了导出再重写全部聊天或再次从 IndexedDB 克隆已加载媒体数组。合并尚在持久化队列中的后台消息快照。
- JSON 按字段/数组/字符串片段生成，分批让出主线程；输出合并为约 64KB 字节块，避免大量小 Blob 片段产生额外内存开销。
- 按实际 UTF-8 字节数逐步检查 10MB 单文件上限，不再生成完整大字符串才检查。
- 增加进度、取消、重复执行保护；下载地址延后释放，提示“已请求下载”而不宣称设备已保存。
- 提供“大记录分卷导出（仅消息）”：每卷目标约 4MB 或最多 10000 条，用户确认保存后再下载下一卷。分卷保留相同会话 ID、原消息 ID，以及卷号、起止索引、总条数；源记录不截断、不删除。分卷器的游标仅在该卷成功生成后推进。
- 旧的可见全量/消息导出函数在 NextRuntime 下统一进入当前聊天数据管理，避免误走整站 ZIP 路径。
- 所有导出操作为只读；失败/取消不执行恢复、清理、删除或覆盖。

## 边界

这仍是轻量聊天备份，不包含消息图片/音频/视频/附件、贴图库与背景图库。分卷只是消息，不代替会话设置备份，也没有在本次新增分卷恢复工具。当前聊天备份仍使用既有 version 1 格式及同 ID 恢复规则。

没有承诺任意大小数据都能在手机中导出：后台会话如未加载，其旧存储格式把全部消息放在一个 IndexedDB 值内，浏览器读取该值仍可能有内存开销；消除这一限制需要后续分条存储适配。没有做真实 iPhone、500MB 或系统内存耗尽测试，不能保证操作系统不会终止页面。
